# Mobile Sales OS experience

- **Status:** Future responsive-web direction; no native app is authorised
- **Principle:** Mobile is simpler than desktop

## Primary mobile navigation

1. **Today** — focus, upcoming Interactions, deal attention and target headline.
2. **Interactions** — prepare, start/finish, capture and debrief.
3. **Actions** — due, approval-required and failed/reconciliation work.
4. **Search** — find or ask across authorised records.

Account, Opportunity, Find, Pipeline, Create and Insights appear as contextual pages
or in a compact More menu; they do not all become bottom-navigation items.

## Contextual priority

- Interaction in ten minutes → **Prepare**.
- Interaction in progress → show only capture state, marker/photo and End.
- Interaction just ended → **Capture this while it's fresh**.
- Customer-facing Action awaits approval → show recipient/consequence and Review.
- No urgent item → show one Daily focus and recent work.

## Layout rules

- one primary action per screen;
- one column, large touch targets and no essential hover;
- summary before detail; secondary panels collapse;
- forms split into short focused steps;
- no wide tables or drag-only boards;
- visible offline/permission/partial state;
- native controls, semantic headings, screen-reader status and visible focus;
- text scaling and reduced motion supported; and
- lock-screen notifications contain no customer detail by default.

## Capability behaviour

- **Find:** search, source review and save; ICP/territory administration stays
  desktop-first.
- **Engage:** review, approve, pause and event capture; campaign authoring stays
  desktop-first.
- **Create:** start from Opportunity and review output; template/layout administration
  stays desktop-first.
- **Pipeline/Insights:** cards and exceptions, not horizontal grids.
- **CRM:** quick stage/next-step review, not bulk import or custom-field design.
- **Manager:** team exceptions and upcoming important Interactions, not dense cohorts.

## Browser and native boundary

Responsive web remains the default. A native app is considered only when measured
browser limits block a high-value capability such as lawful background capture,
screen-lock continuity, encrypted offline media or reliable push. Native is not
required merely for navigation parity.

The current browser Companion already states its foreground and interruption limits.
Future design must preserve deliberate capture, persistent indicators, stop/delete,
device-loss handling and a complete non-recording path.

## First-use test

Within 30 seconds, a new seller should be able to identify today's top item, open an
upcoming Interaction and understand Prepare/Start/Debrief. If explanation or training
is required to discover those actions, the mobile design has failed.
